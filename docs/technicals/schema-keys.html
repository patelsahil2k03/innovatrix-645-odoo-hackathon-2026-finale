1 · Master data

The nouns of the business. accounts has no foreign keys at all — it's the leaf every other table points at, for a different reason each time.

2 · Documents → the ledger

Every document is a header table plus a lines table. Every line carries its own product and account — never the parent document — so editing a product later can't rewrite a line that already posted. Everything funnels into journal_entries, which is the only table the reports actually read.

RelationshipCardinalityWhat it means
sales_orders.id←sales_order_lines.order_id 1–N One order, many line items. Deleting the header cascades to its lines — a line never outlives its document.
sales_orders.id←customer_invoices.so_id nullable 1–N An invoice may trace back to the order that generated it. Nullable on purpose: the mockup requires bills and invoices raisable standalone, with no order at all.
journal_entries.id←journal_lines.entry_id 1–N The actual double-entry: one entry, two or more balanced lines (debits = credits). This is the only table every report reads.
customer_invoices.journal_entry_id→journal_entries.id nullable effectively 1–1 Nullable because a DRAFT invoice hasn't posted yet. Not a DB-level unique constraint, but a partial unique index on journal_entries(source_type, source_id) guarantees one live entry per document from the other side.
journal_entries.id←journal_entries.reversal_of_id self-referencing A posted entry is never edited. A correction is a new entry that cancels it, linked back here — the mistake and the fix both stay visible forever.
journal_lines.account_id N–1 Notice what this table doesn't have: no invoice_id, no bill_id. A line only knows its account — it has no idea what document produced it, which is exactly why reports can't double-count or miss a document type.

RelationshipCardinalityWhat it means
payments.invoice_id / payments.bill_id both nullable Both columns exist, both are nullable, but a CHECK constraint forces exactly one to be set. A payment always settles one thing — never both, never neither.
payments.idempotency_key unique Not a foreign key — a plain unique constraint. A retried "Pay" click can't create a second payment for the same click.
budgets.id←budgets.revision_of_id / revised_with_id self-referencing, both ways A CONFIRMED budget is never silently edited — a revision is a new row, linked both forward and backward to the one it replaces.
contacts.id←users.contact_id nullable effectively 1–1 How the contact portal works: a portal-role user is the same person as a contact, so they only ever see their own documents. Internal staff users leave this null.
users.id←audit_logs.user_id 1–N Every successful write (POST/PATCH/PUT/DELETE) is recorded here automatically by middleware — nobody calls this table directly.

4 · The constraints that matter more than the diagram

Three rules, enforced by the database itself, that no foreign key on its own can express.

One live posting per document

A partial unique index on journal_entries(source_type, source_id), active only where state ≠ 'REVERSED'. One document can have exactly one entry that currently counts — but a reversed entry doesn't block a fresh repost. This is the real double-posting guard, not any single foreign key.

Every UUID is generated before the row exists

Every id is a 36-character string, built in application code, never a database SERIAL. Two people on two machines writing to the same shared database can never collide on an ID — there's no "who gets row 47" race.

Gapless numbers come from a lock, not the primary key

INV/2026/0005 and S00001 are unrelated to any id. A separate number_sequences table is read under SELECT ... FOR UPDATE and incremented atomically, so two backends posting at the same instant never hand out the same number.
